## Outcome

Provide a PostgreSQL-authoritative, per-device FIFO arbiter. At most one root execution may affect a device. Once dispatched, the root retains ownership until device-terminal success/failure/cancellation. Disconnect, timeout, server crash, or lost result are ambiguous and must fail closed in `reconciling`/`blocked`; they never advance the queue without explicit terminal evidence or audited administrative resolution.

Different devices remain independently concurrent.

## Product invariants

1. Exactly one active root per device, admitted atomically and durably by PostgreSQL. Process-local state may cache/observe, never authorize.
2. FIFO is stable per device; separate devices can execute concurrently.
3. Standalone JOB owns the permit through device-terminal `completed`, `failed`, or `cancelled`.
4. Edge WORKFLOW and BATCH own it through their terminal device result.
5. Server-mode WORKFLOW owns one root permit across every child JOB/BATCH, wait, and checkpoint. Children re-enter with the root permit and cannot release or requeue it.
6. Every device-affecting egress is admitted centrally, including raw jobs, task runner/generated workflow, workflow executor, edge workflow, batches, Hydra, app mapping, skills/cascade, orchestrator, screen detection, compiler/recovery runners, and any additional production sender found by G0 inventory.
7. Direct transport send APIs require a typed arbiter permit. A CI/static test rejects new bypasses.
8. Results are checked against device/root ownership and terminal transitions use compare-and-swap. Duplicate, late, or wrong-device results cannot overwrite terminal/reconciling state or release a successor.
9. Crash/restart, disconnect, timeout, and lost results become blocked reconciliation. Startup cannot advance ambiguous roots.
10. Kill/cancel control signals may bypass the normal execution queue only as control egress and must be audited; they cannot carry ordinary UI work.
11. Preserve existing API compatibility where reasonable. `POST /api/jobs` remains `202`/queued and queue/execution status includes state and reason.
12. Queue migrations are durable and idempotent. Startup fails closed if required queue schema is unavailable. Broader migration-engine hardening is documented separately.

## Proposed data model (G0 candidate; FORGE must validate)

- `device_execution_roots`: root id, device id, kind, request/idempotency key, state, FIFO sequence, owner generation, timestamps, terminal/reconciliation reason, metadata. A partial unique index permits only one active/reconciling root per device.
- `device_execution_events`: immutable audit log for admission, claim, send, result, transition, rejection, reconciliation, administrative resolution, and control signals.
- State machine: `queued → claimed → dispatched → terminal(completed|failed|cancelled)`; ambiguous transitions enter `reconciling`/`blocked`. Only explicit evidence/admin resolution may leave ambiguity. Claim and state changes use transactions, row locks, and CAS predicates.
- Permit: opaque root id + device id + monotonic owner generation. Child dispatches reuse it; transport verifies it against DB authority.
- FIFO claim: transactionally choose the oldest eligible queued root only when no active/reconciling root exists for the device. Use PostgreSQL constraints/locking so two server workers yield one winner.

## Threat/risk checklist

- No production ingress can manufacture or bypass a permit.
- Database outage/schema mismatch fails closed.
- Stale worker/result cannot release or mutate a newer root.
- Idempotency cannot create duplicate ownership.
- Administrative resolution is authenticated, explicit, reasoned, and audited.
- Control-signal bypass is narrowly typed and cannot execute UI actions.
- Avoid deadlocks: one device root at a time; deterministic lock order; never wait for another device while holding a root.
